# MISSION — ÉVOLUTION DU PROJET CORISCHOOL

Tu travailles directement sur le projet existant CoriSchool, une plateforme de gestion scolaire développée avec Laravel + Inertia React + Tailwind CSS.

IMPORTANT :
- Tu dois travailler sur le projet EXISTANT.
- Ne recrée pas l'application depuis zéro.
- Ne remplace pas inutilement les fonctionnalités déjà fonctionnelles.
- Avant toute modification, analyse l'architecture et le code existant.
- Réutilise les modèles, contrôleurs, middleware, routes, composants et layouts déjà présents lorsqu'ils sont adaptés.
- Respecte les conventions existantes du projet.
- Utilise Lucide pour les icônes lorsque cela est déjà utilisé dans le projet.
- Conserve une interface professionnelle, moderne, responsive et adaptée au contexte des écoles béninoises.
- Palette visuelle privilégiée : vert / teal / blanc, avec des cartes et états visuels clairs.
- Ne demande pas de confirmation entre chaque étape : analyse, planifie puis implémente progressivement.
- Ne détruis aucune donnée existante.
- Avant les migrations destructives, vérifie les données et privilégie les migrations compatibles avec l'existant.

==================================================
5. MULTI-ÉCOLE / SCHOOL_ID
==================================================

Le système doit fonctionner comme une application multi-école.

Une école est représentée par un enregistrement School.

Toutes les données appartenant à une école doivent être isolées par :

school_id

Un utilisateur appartenant à une école ne doit jamais pouvoir :

- voir les élèves d'une autre école ;
- modifier les notes d'une autre école ;
- voir les enseignants d'une autre école ;
- consulter les parents d'une autre école ;
- consulter les emplois du temps d'une autre école ;
- consulter les données financières d'une autre école.

Ne fais pas confiance uniquement au filtrage frontend.

L'isolation doit être garantie côté serveur.

Vérifie les controllers, queries, policies et middleware.

Lorsque cela est pertinent, utilise le school_id de l'utilisateur authentifié plutôt qu'un school_id fourni librement par le frontend.

==================================================
6. ENREGISTREMENT D'UNE ÉCOLE
==================================================

Ajouter un véritable onboarding d'école.

Le flux attendu :

Landing page
    ↓
Créer mon école
    ↓
Formulaire d'inscription école
    ↓
Création de l'école
    ↓
Création du compte administrateur
    ↓
Association user.school_id
    ↓
Connexion / redirection
    ↓
Dashboard de l'école

Le formulaire doit prévoir au minimum :

- nom de l'école ;
- sigle ou nom court ;
- adresse ;
- ville ;
- département ;
- téléphone principal ;
- email ;
- logo ;
- site web si pertinent ;
- type d'établissement ;
- année scolaire ;
- informations de contact.

Après création :

- l'école doit être créée ;
- le premier utilisateur doit être correctement associé à cette école ;
- le rôle doit être administrateur de l'école ;
- school_id doit être renseigné ;
- le dashboard doit afficher les données de cette école.

Ne crée pas plusieurs bases de données.

Le système doit continuer à utiliser la même base avec school_id.

==================================================
7. GESTION DU PERSONNEL
==================================================

L'administrateur de l'école doit pouvoir gérer son personnel depuis le dashboard.

Créer ou améliorer une section :

Administration → Personnel

Le personnel peut comprendre :

- administrateur ;
- directeur ;
- enseignant ;
- secrétaire ;
- censeur ;
- comptable ;
- autres rôles compatibles avec le système existant.

Avant de créer un nouveau système de rôles, inspecte l'Enum Role existant.

Réutilise-le si possible.

Pour chaque membre du personnel :

- prénom ;
- nom ;
- email ;
- téléphone ;
- rôle ;
- statut actif/inactif ;
- éventuellement photo ;
- identifiants de connexion si le personnel possède un compte.

L'administrateur doit pouvoir :

- créer ;
- modifier ;
- activer/désactiver ;
- consulter.

Lorsqu'un membre du personnel possède un compte :

user.school_id = school.id

Il ne doit jamais être possible de créer depuis l'interface d'une école un utilisateur rattaché à une autre école.

Les permissions doivent être respectées.

==================================================
8. EMPLOI DU TEMPS
==================================================

Ajouter un véritable module d'emploi du temps.

Créer les migrations nécessaires seulement après avoir vérifié les modèles existants.

Le système doit permettre d'associer :

- école ;
- année scolaire ;
- classe ;
- matière ;
- enseignant ;
- jour ;
- heure de début ;
- heure de fin ;
- salle.

Prévoir une structure équivalente à :

timetables

avec les relations nécessaires.

L'emploi du temps doit être accessible selon les droits à :

ADMINISTRATION
- créer ;
- modifier ;
- supprimer ;
- consulter.

ENSEIGNANT
- consulter son emploi du temps.

PARENT
- consulter l'emploi du temps de son enfant.

ÉLÈVE
- consulter son emploi du temps si le portail élève existe déjà.

Interface souhaitée :

- vue hebdomadaire ;
- Lundi ;
- Mardi ;
- Mercredi ;
- Jeudi ;
- Vendredi ;
- Samedi si nécessaire.

Afficher clairement :

heure + matière + enseignant + salle + classe.

Prévoir les validations nécessaires pour éviter les incohérences.

Par exemple :
- heure de fin > heure de début ;
- classe appartenant à la même école ;
- enseignant appartenant à la même école ;
- matière appartenant à la même école ;
- année scolaire cohérente.

9. PHOTO DES ÉLÈVES
==================================================

Ajouter la possibilité d'ajouter une photo à chaque élève.

Avant de modifier la base, inspecte le modèle Student existant.

Si nécessaire, ajouter un champ du type :

photo_path

Utiliser le stockage Laravel approprié.

Éviter de stocker les images en Base64 dans la base de données.

La photo doit être accessible dans :

- fiche élève ;
- liste élèves ;
- profil parent ;
- gestion des présences si pertinent ;
- recherche élève ;
- administration.

Prévoir :

- upload ;
- validation du type MIME ;
- taille maximale raisonnable ;
- remplacement de la photo ;
- suppression de l'ancienne photo lorsqu'elle est remplacée ;
- suppression propre lorsque l'élève est supprimé si cela est approprié.

Utiliser le système Storage Laravel existant.

==================================================

Inspecte d'abord la structure actuelle des parents/tuteurs.

Le système doit permettre de conserver deux numéros :

phone_primary
phone_secondary

ou une nomenclature équivalente cohérente avec les modèles existants.

Ne crée pas de doublon si la structure actuelle permet déjà de le faire proprement.

L'interface parent/tuteur doit permettre :

- numéro principal ;
- numéro secondaire.

Afficher clairement lequel est principal.

Les deux numéros doivent être disponibles pour les fonctionnalités de communication/SMS lorsqu'elles seront utilisées.

Ne mets pas de logique automatique de basculement SMS sans vérifier comment le système SMS existant fonctionne.
