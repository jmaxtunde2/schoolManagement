# CORISCHOOL — COMPLETE COMMUNICATION & AUTOMATIC PARENT NOTIFICATION SYSTEM

## 1. OBJECTIVE

Implement a complete communication system for CoriSchool that automatically notifies parents when new academic results become available, while minimizing communication costs.

The system must combine:

- In-app notifications
- SMS notifications
- WhatsApp notifications
- Email notifications
- Communication budgets per school
- SMS balance monitoring
- WhatsApp budget monitoring
- Automatic fallback between channels
- Daily aggregation of validated evaluations
- Parent notifications at 17:00
- Message batching
- Communication history and cost tracking
- Platform Admin monitoring
- Automatic cleanup of old in-app notifications

The architecture must be reusable later for:

- Absences
- Retards
- Bulletins
- Results
- Announcements
- Fee reminders
- Other school notifications

For the first implementation, only **validated evaluation/grade notifications** are required.

---

# 2. CORE BUSINESS VALUE

The core CoriSchool value proposition is:

> **Chaque évaluation validée est automatiquement destinée à être communiquée aux parents.**

However, CoriSchool must NOT send one SMS for every validated evaluation.

Instead:

> **At 17:00 every day, CoriSchool collects all newly validated evaluations, groups them by student, and sends one consolidated notification per student and parent.**

Therefore:

### Bad behavior

```text
Maths validated
→ SMS

SVT validated
→ SMS

French validated
→ SMS

English validated
→ SMS
```

This generates unnecessary communication costs.

### Desired behavior

```text
Maths validated
SVT validated
French validated
English validated

              ↓

            17:00

              ↓

       Group by student

              ↓

      One consolidated message

              ↓

       Father + Mother
```

---

# 3. NO MANUAL "NOTIFY PARENTS" ACTION

There must NOT be a manual:

```text
Notifier les parents
```

button that requires the teacher, Admin, Censeur or Directeur to trigger parent notification.

The notification process is automatic.

The approver's responsibility ends with:

```text
Validate / Approve
```

Once the evaluation is validated, CoriSchool automatically marks it as eligible for the next parent notification cycle.

Example:

```text
Teacher submits evaluation
        ↓
Admin/Censeur/Directeur validates
        ↓
Evaluation = validated
        ↓
Notification = pending
        ↓
17:00 daily process
        ↓
Parent notification
```

---

# 4. VALIDATED EVALUATION = READY FOR NOTIFICATION

When an authorized user validates an evaluation:

- Admin
- Censeur
- Directeur

the system must automatically register:

```text
notification_status = pending
```

or an equivalent status according to the existing database architecture.

Do not create a separate manual notification workflow.

The evaluation must remain linked to the notification lifecycle.

---

# 5. DO NOT SEND IMMEDIATELY

If an evaluation is validated at:

```text
10:15
```

do NOT immediately send an SMS, WhatsApp message or email.

The evaluation becomes:

```text
pending_notification
```

and waits for the daily notification process.

This allows multiple evaluations for the same student to be consolidated.

---

# 6. DAILY ARTISAN COMMAND

Create:

```bash
php artisan corischool:notify-validated-evaluations
```

Schedule it every day at:

```text
17:00
```

The command must:

1. Find validated evaluations not yet included in a successful parent notification.
2. Respect the daily notification window.
3. Group evaluations by school.
4. Group evaluations by student.
5. Retrieve the student's eligible parents.
6. Build one consolidated notification per student/recipient.
7. Create the in-app notification.
8. Select the appropriate external communication channel.
9. Queue external notifications.
10. Process recipients in batches.
11. Track delivery and cost.
12. Mark evaluations correctly only after successful processing.

---

# 7. DAILY WINDOW

The daily cycle is:

```text
00:00 → 17:00
```

During this period:

```text
Evaluation validated
        ↓
notification_status = pending
```

At:

```text
17:00
```

the command processes pending evaluations.

Evaluations validated after 17:00 normally belong to the next day's notification cycle.

Do not send them immediately.

---

# 8. GROUPING BY SCHOOL AND STUDENT

The main grouping key should be:

```text
school_id
+
student_id
+
notification_date
```

Do NOT group multiple students together.

Example:

```text
Jean Dupont
→ one consolidated notification

Marie Koffi
→ one consolidated notification

Paul Mensah
→ one consolidated notification
```

Even if all three students belong to the same class.

---

# 9. EXAMPLE OF DAILY AGGREGATION

Suppose Jean Dupont has five evaluations validated during the day:

```text
Mathématiques → 15/20
SVT           → 12/20
Français      → 14/20
Anglais       → 16/20
Histoire      → 13/20
```

At 17:00, CoriSchool must NOT send five messages.

It creates one notification containing:

```text
CoriSchool via [Nom de l'école]

Nouvelles notes de Jean Dupont :

Mathématiques : 15/20
SVT : 12/20
Français : 14/20
Anglais : 16/20
Histoire : 13/20

Consultez votre espace parent :
corischool.com
```

---

# 10. PARENT RECIPIENTS

After grouping by student, retrieve the student's eligible parents.

Possible cases:

```text
Father only
Mother only
Father + Mother
```

If both parents have valid communication information:

```text
Father → receive notification
Mother → receive notification
```

The same consolidated student notification is sent to both.

If father and mother have the same phone number:

```text
send only once
```

Do not create duplicate external messages.

---

# 11. ONE SMS SEGMENT MAXIMUM

The external SMS notification must never exceed:

```text
ONE SMS SEGMENT
```

Do not automatically split one notification into:

```text
SMS 1
SMS 2
SMS 3
```

The purpose is to control communication costs.

Create a configurable setting:

```text
MAX_NOTIFICATION_SMS_LENGTH
```

The default should correspond to a single SMS segment.

Prefer GSM-7-compatible characters where possible.

Avoid unnecessary emojis and special Unicode characters because Unicode SMS messages have a much smaller single-message capacity.

---

# 12. IF ALL RESULTS FIT

If all validated evaluations fit within the configured SMS limit, send the detailed consolidated message.

Example:

```text
CoriSchool via [Nom de l'école]
Nouvelles notes de Jean Dupont :
Mathématiques 15/20, SVT 12/20, Français 14/20.
Consultez votre espace parent : corischool.com
```

The application URL must be configurable.

Do not hard-code school names, students, subjects or scores.

---

# 13. IF RESULTS DO NOT FIT

If there are too many evaluations to fit into one SMS segment:

DO NOT send multiple SMS messages.

Instead, send a short alert:

```text
CoriSchool via [Nom de l'école] :
De nouvelles notes de Jean Dupont sont disponibles.
Consultez votre espace parent : corischool.com
```

The complete results remain available inside the parent dashboard.

Therefore:

```text
SMS
→ alert

Parent dashboard
→ complete results
```

This preserves the one-SMS maximum.

---

# 14. IN-APP NOTIFICATION IS ALWAYS CREATED

The parent must always receive an in-app notification.

The in-app notification is not subject to the SMS length limitation.

Example:

```text
Nouvelles notes disponibles

Jean Dupont

Mathématiques : 15/20
SVT : 12/20
Français : 14/20
Anglais : 16/20
Histoire : 13/20

[Voir les résultats]
```

The in-app notification should link directly to the relevant parent/student results page when possible.

---

# 15. IN-APP NOTIFICATION RETENTION

In-app notifications should remain visible in the active notification interface for:

```text
15 days
```

After 15 days:

- remove/archive them from the active notification list
- do not destroy important audit/communication history

Communication logs and audit records must remain available for administrative history and reporting.

Create a scheduled cleanup command/job if one does not already exist.

---

# 16. COMMUNICATION CHANNEL PRIORITY

CoriSchool must use the following communication strategy:

```text
IN-APP
   ↓
always used

EXTERNAL
   ↓
SMS
   ↓
WhatsApp
   ↓
Email
```

In-app notification is always created.

For external notification:

### Priority 1

Use SMS when SMS is enabled and sufficient balance is available.

### Priority 2

If SMS is unavailable because of insufficient balance, provider failure, or configured disablement:

```text
WhatsApp
```

### Priority 3

If WhatsApp is unavailable:

```text
Email
```

Do not send the same notification through all external channels unless explicitly configured.

The objective is fallback, not duplication.

---

Store them in configurable settings/database records.


# 18. SMS BALANCE MONITORING

Create a daily Artisan command:

```bash
php artisan corischool:check-sms-balances
```

This command must:

1. Query the SMS provider balance.
2. Update the school's current SMS balance.
3. Record the last balance check.
4. Update SMS availability.
5. Trigger fallback when the balance is too low.
6. Make the information visible to Platform Admin.

Initial rule:

```text
SMS balance < 500 FCFA
        ↓
Disable SMS
        ↓
Activate WhatsApp fallback
```

To avoid constant switching around the threshold, use hysteresis.

Recommended:

```text
SMS disabled below 500 FCFA

SMS reactivated when balance >= 1,000 FCFA
```

Both thresholds must be configurable.

---

# 19. SMS BUDGET VS PROVIDER BALANCE

Keep these concepts separate:

### School communication budget

How much CoriSchool has allocated for the school.

Example:

```text
3,000 FCFA
```

### Provider balance

Actual available balance at the SMS provider.

Example:

```text
1,850 FCFA
```

Platform Admin should be able to see both.

---

# 21. COMMUNICATION FALLBACK

The fallback logic should be:

```text
Try SMS
   ↓
SMS unavailable?
   ↓
Try WhatsApp
   ↓
WhatsApp unavailable?
   ↓
Try Email
```

Possible SMS unavailability reasons:

- balance below threshold
- provider disabled
- provider API failure
- school SMS channel disabled
- temporary provider failure

Possible WhatsApp unavailability reasons:

- budget exhausted
- provider disabled
- recipient unavailable
- provider API failure

Email should be the final external fallback when an email address is available.

---

# 22. MESSAGE BATCHING

External messages must be processed in batches of:

```text
25 recipients
```

Example:

```text
200 recipients

Batch 1 → 25
Batch 2 → 25
Batch 3 → 25
...
Batch 8 → 25
```

Wait:

```text
10 minutes
```

between batches.

Do NOT implement:

```php
sleep(600);
```

inside a queue worker.

Use Laravel delayed jobs.

Example:

```text
Batch 1
delay = 0

Batch 2
delay = 10 minutes

Batch 3
delay = 20 minutes

Batch 4
delay = 30 minutes
```

This prevents workers from being blocked unnecessarily.

---

# 23. COST OPTIMIZATION

Aggregation MUST happen before message counting and cost calculation.

Example:

```text
5 evaluations
1 student
2 parents
```

Without aggregation:

```text
5 × 2 = 10 messages
```

With aggregation:

```text
1 × 2 = 2 messages
```

Savings:

```text
8 external messages
```

This aggregation is an essential part of the CoriSchool business model.

---

# 24. NOTIFICATION LIFECYCLE

Use a reliable notification lifecycle.

Recommended:

```text

    ↓

    ↓

    ↓

    ↓
sent
    ↓

```

If a provider fails:

```text

```

The system must support retry/fallback.

Do NOT consider a notification successfully sent merely because a Laravel job was created.

---

# 26. FAILURE HANDLING

If an external notification fails:

Do NOT mark the evaluations as successfully notified.

Keep them associated with the notification attempt.

Example:

```text
SMS
failed
   ↓
WhatsApp fallback
   ↓
success
```

If WhatsApp also fails:

```text
Email fallback
```

If all external channels fail:

```text
In-app notification remains available
notification = failed
```

The system must retain the error message/provider response where appropriate.

---

# 27. IDEMPOTENCY — VERY IMPORTANT

The daily command may be executed more than once.

It must NOT send duplicate notifications.

Before creating a new notification batch, verify that the evaluation has not already been successfully included in a previous notification.

Use appropriate database constraints/status checks.

The process must be safe if:

```bash
php artisan corischool:notify-validated-evaluations
```

is accidentally executed twice.
